# API Contracts
- Staff-session configuration failures retain `code: configuration_unavailable` and may include `configuration_fields`, an array of invalid names from `APP_ENV`, `SESSION_SECRET`, `STAFF_PASSCODE`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`. No values are returned. A failed login rate-store operation returns `staff_rate_limit_unavailable` (503); it never bypasses the check.

All APIs return JSON, controlled `code`/`message`/safe `request_id` failures and no-store security headers. Writes require same origin; no wildcard CORS. IDs are UUIDs; amounts are positive exact decimal USD strings bounded to merchant-safe limits. Every complete operation has a deadline and input-size bound.

- `POST /staff-session`: `{passcode}`; success `{authenticated:true}` and signed short-lived HttpOnly cookie. `GET` checks current session; `DELETE` clears it. Missing configuration 503; rejected session 401; throttled login 429. Staff endpoints require that server-verified session.
- `GET /payment-link?id=UUID`: allowlisted `{id,tokenizer_origin,order_number,amount,currency,customer_name,customer_email,status,retref,card_last4,paid_at,receipt_sent}`. Effective statuses pending/processing/review/paid/unavailable. 404 for missing/expired/cancelled; malformed UUID 400. Existing paid links remain receipt-readable. The server-owned tokenizer_origin is exactly the production or UAT CardPointe origin selected by APP_ENV; frontend and gateway environment cannot silently diverge.
- `POST /charge`: `{paymentLinkId,amount,cardholderName,token,expiry,cvv2,zip}`; The displayed/authorized amount must exactly match the current canonical invoice before charging; the gateway amount is always derived from the database. Name on card is a separate required trimmed string (1–30 characters) passed as gateway `name`; the processor does not document issuer name-match verification. Claim before gateway request. Success `{success:true,retref,card_last4,paid_at,receipt_sent}`; existing active/unknown attempt 202 `{success:false,code:'payment_pending',status:'processing'}`; definite decline 402; invalid fields 400; unavailable 404. Approval/write ambiguity never becomes a safe-to-retry generic failure.
- `POST /analyze-invoice`: bounded `{text}` or `{imageBase64}`; validated fields plus `review_required`/`warnings`; no model/provider content echoes. Partial/missing values require review. Staff session required.
- `POST /create-link`: `{request_id,order_number,amount,customer_name,company_name,customer_email,attachments,send_email}`. Return `{id,email_sent,email_status}` even if notification fails after insertion. Same request UUID + same validated payload yields same link; changed payload under same UUID 409. Attachments are readable reviewed files independent of parser success; bounded base64/filename/type rules.

## Supabase boundary
Service-only RPCs claim/finalize financial attempts, resolve declines/review, atomically rate-limit requests and create/recover a link. Existing direct frontend Supabase access is unused and removed. Schema migration is required and retained during rollback; secrets and raw payment inputs never appear in RPC arguments.
