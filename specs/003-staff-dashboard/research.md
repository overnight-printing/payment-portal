# Research: Staff Dashboard

Phase 0 read-only research delegated to `dashboard_research`; local source/migration inspection, no live data.

- **Decision**: Reuse staff gate in CreateLink for `/dashboard`, rather than introducing a second authentication system. Disable file-drop/creation recovery effects in dashboard mode. **Rationale**: Same sign-in and failure behavior with minimal code. **Alternative**: New auth provider/layout refactor adds unrelated change.
- **Decision**: Add an explicit email status, preserve legacy boolean and existing creation RPC. **Rationale**: False cannot distinguish old unknown history, failed sends or no email request. Conditional writes prevent concurrent failure from downgrading acceptance. **Alternative**: Infer from request_id or boolean; rejected because historical truth is unavailable.
- **Decision**: Service-only SECURITY INVOKER RPC with one read snapshot and literal search. **Rationale**: Existing service role has required reads; no additional elevated privileges needed. Summaries remain consistent across pages. **Alternative**: Frontend loads all records; rejected for privacy and unbounded responses.
- **Decision**: Read payment attempts without reconciliation. **Rationale**: Dashboard must be read-only and never trigger gateway traffic or payment side effects. Paid wins, unresolved attempts precede expiry/cancellation.
- **Decision**: Native HTML and existing CSS tokens, guided by ui-styling accessibility patterns. **Rationale**: Labels, focus and responsive cards work without new libraries. No unresolved decisions.

Workspace Phase 0 read-only research (`workspace_research`): explicit per-send UUID avoids suppressing deliberate resends under the original link-based key. Pending/unknown attempts never retry provider automatically, even after provider idempotency expires; terminal request replay returns stored outcome. Initial and later sends share atomic claim/finish. Latest email outcome must not be hidden by ever-accepted boolean. Original attachments are not stored; later email sends only the payment link. Customer grouping uses normalized email and separate missing-email identities.

## Operations research
Decision: extend durable email ledger with kind/provider/recipient metadata; signed webhook tags bind early events, native Web Crypto verifies bounded raw UTF-8 with HMAC-SHA256 id.timestamp.body, +/-300 seconds. Preserve transport vs delivery and per-recipient facts; no raw payloads. Rationale: current provider-only receipt identity lasts 24h and staff alerts have two independently delivered recipients. Known-ID retrieval checks recipients/tags; missing-ID uncertainty cannot be safely retried. Alternatives: provider-only locks and elapsed-time retries rejected. Sources: https://resend.com/docs/webhooks/verify-webhooks-requests ; https://docs.svix.com/receiving/verifying-payloads/how-manual ; https://resend.com/docs/webhooks/emails/delivered ; https://resend.com/docs/api-reference/emails/retrieve-email ; https://resend.com/docs/dashboard/emails/idempotency-keys ; https://www.resend.com/changelog/webhook-event-visibility .

Decision: atomic row-locked cancel/replace and unique successor; preserve original and exclude cancelled from outstanding totals. Rationale: payment/email claims already lock invoice first, and original dashboard sums would double-count replacements. Staff check uses private record read because public lookup rejects expired links; inquiry-only matching capture may resolve uncertainty without unlocking. Export one bounded filtered SQL snapshot with quoted formula-safe fields. Alternatives: renewing original expiry loses history; client paging exports can skip/duplicate rows; neither used. PostgreSQL locking: https://www.postgresql.org/docs/17/explicit-locking.html .

Recent-history decision: reuse deployed limit/date RPC contracts; no schema/API expansion. Calculate Seattle today using Intl.DateTimeFormat parts and subtract 29 UTC calendar days, avoiding DST errors and machine-local timezone assumptions. Keep global financial summary distinct from filtered recent list; overview card drilldowns explicitly use all time. Native select/date inputs and existing pagination controls suffice; no date library or new table dependency.
