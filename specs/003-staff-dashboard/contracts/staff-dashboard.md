# Staff Dashboard Contracts

## GET /staff-links
Same-origin protected staff endpoint in Pages and shared Worker. No request body. Query: `search` literal text <=100 chars, `payment` all/paid/unpaid/processing/review/expired/cancelled, `email` all/accepted/not_requested/failed/unknown (unknown includes pending), `offset` decimal integer 0..100000, `limit` decimal integer 1..50, default25. Invalid queries:400; unsigned/expired session:401; rate limit:429; unavailable/malformed database:503. Errors use existing sanitized code/message/request_id shape; no history on errors. Responses no-store. No gateway/email side effects.

200: `{summary:{total:3,paid:1,unpaid:2,paid_cents:1000,unpaid_cents:2500},total:2,offset:0,limit:25,links:[{id:UUID,order_number:"INV-1",customer_name:null,customer_email:null,amount:"10.00",created_at:null,paid_at:null,payment_status:"expired",email_status:"unknown"}]}`. Counts and cents are nonnegative safe integers; amount positive exact decimal USD. Dates nullable ISO timestamps. Status values constrained above, plus unpaid (row) and pending (email).

`portal_staff_dashboard(p_search text,p_payment text,p_email text,p_offset integer,p_limit integer)` returns one JSONB object. Bounded arguments validated in API and SQL. EXECUTE only service_role; invoker rights; table grants unchanged. Query uses one read snapshot; overall totals ignore filters; newest first with deterministic ID ties.

## Link creation/recovery amendment
Existing POST /create-link request remains compatible. Initial email uses the same durable per-request claim/finish as explicit dashboard sends. Provider/finish uncertainty returns pending (Unconfirmed); request replay never blindly retries provider. Link-only initializes not_requested only when unknown. GET recovery adds email_status alongside id/email_sent. Existing six-argument portal_create_link signature and financial flows remain unchanged. See workspace contracts below for current email/date/customer/detail shapes.

## Frontend
`/` and `/dashboard` show Overview behind the same gate; `/send` embeds creation, `/invoices` tracks records and `/customers` opens grouped/scoped history. Native nav links, labelled search/payment/email controls, summary cards, semantic table on desktop with mobile stacked rows, bounded paging and refresh. Copy uses clipboard or selectable fallback URL. No customer records written to storage. Known routes only; existing public /pay/:id unchanged.

## Workspace amendment

GET /staff-links adds optional `start`/`end` YYYY-MM-DD Seattle dates (inclusive), `customer` exact normalized customer key <=300 chars, `view` links/customers. Payment adds attention. Limit defaults25, bounded1..50. Overall summary adds sent and attention counts. Customer response uses `customers` instead of links, with key,name,email,total,paid,unpaid,paid_cents,unpaid_cents,last_created_at. Customer grouping is email lower(trim(email)), else link:<uuid>. Base links include expires_at and last_email_at; latest event overrides legacy status. Null legacy dates/contact fields allowed. Summary ignores filters.

GET /staff-link?id=UUID is staff-only, rate-limited, no-store. Returns `{link:<allowlisted dashboard row>,emails:[{request_id,state,created_at,finished_at}]}` newest first, max20. No gateway data or raw responses. Missing404, unauthorized401, DB503 sanitized.

POST /send-link-email requires same Origin, staff cookie, bounded JSON and UUID link/request IDs. No client recipient/amount/subject override. Durable SQL claim verifies pending/unexpired/uncancelled/no active payment attempt and serializes same-link sends. Existing terminal request replays recorded state; pending blocks provider call. Response `{id,email_status,email_sent}` where pending means Unconfirmed. Link unavailable/lifecycle conflict409; malformed400, unauthorized401, throttle429, unavailable503. Provider ambiguity or finish failure remains pending. Only explicit new request after a conclusive outcome can resend. Provider idempotency identity is request-based. Attachments only available for original creation; later send uses stored invoice details and URL. No emails are actually sent during local validation.

RPCs: portal_staff_dashboard trailing defaults p_start date,p_end date,p_customer text,p_view text; portal_staff_link(uuid) read snapshot; portal_claim_link_email(uuid,uuid); portal_finish_link_email(uuid,text). New table portal_link_emails service-only, states pending/accepted/failed and immutable request/link identity. Claim locks link, finish locks link then event. A pending send is a durable lock; no timed release or automatic resend. Ever-accepted boolean remains compatibility data; latest outcome/timestamp derive from events.

## Internal payment confirmation mail
Existing staff sender/recipients and `staff-receipt-<link UUID>` idempotency are retained. Staff mail subject `[Paid] Invoice #<order_number> - $<exact two-decimal amount>`. HTML table and plain text contain Invoice Number(s), Amount Paid (USD), Payment Method (credit card with masked last four only when available), Customer / Company (combined stored value), Customer Email and Payment Reference. No staff payment-time row. Customer subject remains `Payment received: Invoice #<order_number>` with existing recipient and `receipt-<link UUID>` identity; dedicated customer receipt includes amount, invoice, customer, masked method, reference and date when recorded. Both use the existing HTTPS logo, inline email-safe tables, Arial and navy/blue; all dynamic HTML is escaped and long fields wrap. Unknown details are never invented. Request mail and all browser/API contracts remain unchanged.

Receipt display refinement: no literal USD labels in confirmation HTML/text; both audiences use a centered navy payment/amount header with circled check and no STAFF CONFIRMATION label. Audience-specific details remain; currency processing, subjects and recipients are unchanged.
Staff subject now `[Paid] <recorded customer/company or Customer> - Invoice #<order_number> - $<comma-grouped two-decimal amount>`. Reject control characters and collapse extra whitespace in the subject name; invalid or missing names use Customer. Both receipt HTML/text use grouped display amounts; subjects/amount display do not change financial processing.

## Operations contracts
POST /send-receipt-email {payment_link_id,request_id} -> {id,email_status,email_sent}; confirmed paid only, customer recipient server-owned. Initial/explicit sends have durable per-kind claims.
POST /check-email-status {payment_link_id,email_request_id} -> {id,email_status,code}; known provider ID read only, validated request tags/recipient. Missing ID -> provider_review; no retry/unlock.
POST /check-payment {payment_link_id} -> {id,payment_status,code}; inquiry only, exact captured amount/reference required; unresolved stays locked.
POST /cancel-link {payment_link_id} -> {id,cancelled:true}; unpaid/no active attempt, repeat harmless.
POST /replace-link {payment_link_id,request_id} -> {id,replaced_id}; expired unpaid/no active attempt; same successor on replay/races, no email.
GET /staff-export with existing invoice search/payment/email/start/end/customer filters -> UTF-8 BOM quoted CSV across all matches, max10,000 or 413. No URLs/payment credentials. Staff endpoints require session and mutations same-origin; no-store/rate-limit/sanitized errors.
POST /resend-webhook signed Svix headers + raw JSON -> {received:true} after durable verification/persistence. Supported sent/delivered/delivery_delayed/bounced/failed/complained/suppressed; ignored other valid events return success. Verify exact body, timestamp +/-300s, each v1 HMAC candidate; missing config fails closed. data.tags object contains portal_request, portal_link, portal_kind and portal_app=payment_portal. Match expected recipient/provider under transaction; unknown/mismatched associations do not change records. Dedupe svix-id+recipient. Do not store raw body or provider descriptions.
Detail/list rows add receipt_status, attention_reasons (allowlisted codes), replaces_link_id/replaced_by optional UUID. History entries add kind, delivery_status and provider-check availability; no provider IDs exposed. Email filter supports accepted/delivered/bounced/failed/delayed/complained/suppressed/pending/unknown/not_requested. Receipt outcomes are separate from payment-link outcomes. Summary/customer add cancelled count; total=paid+unpaid+cancelled; outstanding counts/cents exclude cancelled. Detail includes safe payment reference/time/masked digits for paid only via server receipt read, never tokens/raw gateway output.

Email status filtering matches the customer receipt for paid rows and the payment-link email for other rows, matching the visible Email column. CSV amounts remain canonical two-decimal numbers.

The sent filter groups Accepted/Delivered for the relevant customer email (receipt when paid, payment link otherwise), exactly matching summary.sent and the Emails accepted overview card. Email history timestamps are labelled Attempted; delivery event timestamps remain stored separately.
